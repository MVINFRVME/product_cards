# Решения

## Главная идея

Модель не отвечает за факты. Список характеристик переносит в карточку код, ровно как во входе. Модель пишет только связный текст: заголовок, описание, поисковые запросы и блок для менеджера. После ответа модели код сверяет этот текст со входными данными и вырезает всё, чего во входе нет. Так выполняется главное требование задания — не выдумывать технические характеристики.

## Модель

Одна LLM — `openai/gpt-oss-120b` через Groq. Почему так:

- у Groq бесплатный ключ, проверяющему не нужно ничего оплачивать, чтобы запустить проект; получить ключ: https://console.groq.com/keys (войти, нажать «Create API Key», скопировать ключ, начинается с `gsk_`);
- Groq отвечает быстро: карточка вместе с повторным запросом собирается за 5–20 секунд;
- `gpt-oss-120b` — крупная модель, которая нормально пишет по-русски и поддерживает ответ в режиме JSON.

Ключ лежит в `.env`, файл указан в `.gitignore`; в репозитории только `.env.example`. Модель задаётся переменной `GROQ_MODEL`, поэтому её можно сменить без правки кода. На бесплатном тарифе у Groq суточный лимит токенов; если он кончится, сервис так и скажет и назовёт время, через которое можно повторить.

## Неполные данные

Пустая строка, строка из пробелов и `null` в характеристиках становятся значением «данных нет». Пустые название, производитель и описание тоже не останавливают сборку: контент-менеджеру полезнее черновик с пометками, чем отказ. Все пропуски перечислены в блоке «Что уточнить перед публикацией»; если пропусков нет, на странице зелёная плашка «Все поля заполнены».

Отказ только в одном случае: заполнено вообще ничего — ни названия, ни производителя, ни описания, ни одного значения характеристики. Тогда сервис отвечает «Нечего собирать» и не тратит запрос к модели.

«Что уточнить» и список вырезанного — служебные подсказки для контент-менеджера. На странице они показаны отдельными блоками, в API лежат в поле `gaps`, а в копируемый текст и Markdown не попадают, чтобы их случайно не вставили на сайт вместе с карточкой.

Значения характеристик переносятся как есть, единицы измерения сервис не угадывает и не проверяет. Если во входе `"диапазон измерений": "0–1,6"`, в карточке так и будет `0–1,6`, а «МПа», дописанные моделью, вырезаются как чужое значение: угадать единицу — то же самое, что выдумать характеристику. Ошибка во входе вроде «диаметр корпуса: 100 км/ч» тоже уйдёт в карточку без изменений; поймать её можно только справочником характеристик (см. «Что можно улучшить»).

## Промпт

Системный промпт из `app/prompts.py`:

```text
Вы готовите черновик карточки товара для B2B-магазина контрольно-измерительных приборов.
Пишите по-русски, деловым языком, без рекламных превосходных степеней.
Технические значения берите только из блока «Разрешённые факты» в сообщении пользователя.
Нельзя добавлять типичные для такого прибора параметры: класс точности, питание, степень защиты, материал, ГОСТ, интерфейс, присоединение, погрешность, взрывозащиту, отраслевое применение и любые числа с единицами, которых нет в фактах.
Пометку «данных нет» ставьте только у полей из блока «Пропуски» и у характеристик, у которых в фактах уже написано «данных нет». Не перечисляйте чужие типичные параметры списком «питание / ГОСТ / IP: данных нет», если их не было во входе.
Не подставляйте правдоподобную замену и не используйте знания о производителе или серии.
Ответ — один JSON-объект без пояснений и без markdown. Поля:
{"seo_title":"","seo_description":"","search_queries":[""],"commercial_block":""}
seo_title — не длиннее 70 символов, только название, производитель и факты из списка.
seo_description — от 800 до 1200 символов. Объём набирайте пересказом разрешённых фактов и прямым перечислением пробелов. Пробелы перечислите один раз, одним предложением. Одну характеристику не повторяйте разными словами. Не заполняйте объём новыми характеристиками.
Не пишите отраслевые условия вроде «промышленные» или «нормативные» и не называйте резьбу словами (четвертьдюймовая, полудюймовая), если такой формулировки нет в фактах.
Не пишите про монтаж, установку, совместимость с другим оборудованием и надёжность конструкции: из размеров и резьбы это не следует.
search_queries — от 3 до 5 строк. Только название, производитель и известные характеристики.
commercial_block — 2–3 предложения для менеджера по продажам: кому подходит прибор и какие задачи он решает (по назначению из фактов), и какие 2–3 характеристики из фактов важны при подборе. Не повторяйте описание дословно и не называйте отрасли, среды и сферы применения, которых нет в фактах. Если назначения нет, так и напишите: по назначению данных нет.
Список характеристик в JSON не включайте: его соберёт программа из входа.
```

Сообщение пользователя собирает код: только переданные факты и уже найденные пропуски. Пример для `data/manometer_incomplete.json`:

```text
Разрешённые факты:
Название: Манометр показывающий DM 02
Производитель: данных нет
Описание: данных нет
Характеристики:
- диапазон измерений: 0–1,6 МПа
- класс точности: данных нет
- присоединение: данных нет
- диаметр корпуса: 100 мм

Пропуски, которые нужно явно назвать в seo_description:
- Производитель: данных нет
- Описание: данных нет
- класс точности: данных нет
- присоединение: данных нет
```

Если длина, число запросов или чужие значения не сходятся, программа один раз отправляет повторный запрос: тот же системный промпт и факты, предыдущий ответ модели и замечания проверки. Пример:

```text
Предыдущий ответ нельзя отдавать контент-менеджеру. Верните новый JSON той же формы.
Не добавляйте технических значений, которых нет в разрешённых фактах. Если факта нет, оставьте формулировку «данных нет».
Замечания:
- seo_title сейчас 74 символов, нужно не больше 70.
- В поле seo_description есть значения не из входных данных: «монтаж». Удалите их и не заменяйте другими характеристиками.
```

Повтор не разрешает добавлять факты. Второго повтора нет: что осталось после него, вырезает код.

Параметры запроса: `temperature=0.2` (текст должен быть предсказуемым, а не творческим), ответ в режиме JSON (`response_format=json_object`; если Groq его не принял, запрос повторяется без него, а JSON достаётся из текста), `reasoning_effort=low` (без него Groq иногда возвращал пустой ответ), `max_tokens=4000`.

## Проверка после модели

Код сверяет заголовок, описание, блок для менеджера и запросы со входом и ищет:

- числа с единицами, которых нет во входе («2,5 МПа», «36 В»);
- резьбу, маркировку IP и номер ГОСТ не из входа, в том числе резьбу словами («четвертьдюймовая» при отсутствии G1/4);
- класс точности с чужим числом;
- утверждения на темы, о которых во входе ничего нет: монтаж, промышленное и отраслевое применение, технологические процессы, взрывозащита, нержавеющая сталь, газ, температура, погрешность и подобные;
- противоречия входу: «класс точности — данных нет» при переданном классе 1,5 или «по назначению данных нет» при заполненном описании.

Число или маркировка вырезаются из предложения; если после этого остался обрывок вроде «Присоединение.», он удаляется целиком. Если найдена чужая тема, удаляется всё предложение: без неё фраза теряет смысл или остаётся полуправдой. Замена из знаний модели не подставляется.

Всё вырезанное показано на странице свёрнутой строкой «Убрано из текста модели: N фраз». В раскрытом виде — короткое пояснение и по каждой фразе две строки: что убрано (предложение целиком) и почему, например «здесь утверждение про монтаж, а во входных данных об этом ничего нет». Контент-менеджер видит, что текст правили, и может вернуть фразу вручную, если она верна.

## Как собирается текст

- **Повторы.** Модель часто добирает объём пересказом одного и того же. Одинаковые и близкие по смыслу предложения, в том числе повторы пропусков («производитель — данных нет» в трёх формах), остаются один раз.
- **Объём 800–1200.** Запрет на выдумки и коридор объёма конфликтуют: на бедном входе модель либо не добирает объём, либо добирает его правдоподобными характеристиками. Если описание короче 800 символов, код добавляет абзац для покупателя: характеристики из входа и нейтральные фразы магазина про подбор, заказ и консультацию. Новых характеристик в нём нет. Текст честный, но суховатый.
- **Блок для менеджера.** Должен отвечать на вопрос задания «кому подходит и какие задачи решает». Если модель вернула пустой блок, в нём всё вырезано или она просто повторила описание из входа, код собирает блок сам: «Подходит для задач <назначение из описания>. При подборе важны: <до четырёх характеристик из входа>». Если назначения во входе нет, так и пишется.
- **Поисковые запросы.** Запросы с чужим значением отбрасываются. Если осталось меньше трёх, добавляются запросы из названия, производителя и известных характеристик.

## Замер устойчивости

Насколько модель слушается промпта. Каждый из трёх входов из `data/` прогнан через `openai/gpt-oss-120b` по 3 раза (9 карточек) на текущем промпте.

Карточка собирается в несколько шагов: модель пишет текст → код проверяет его по требованиям задания (заголовок до 70 символов, описание 800–1200, 3–5 запросов, нет значений не из входа) → если есть замечания, модель один раз получает их и переписывает → код вычищает то, что осталось. Таблица сравнивает, что модель выдаёт сама с первой попытки и что в итоге получает пользователь.

| Вход | Модель с первой попытки выполнила все требования | Пользователь получил карточку по требованиям | Код вырезал фраз | Среднее время |
|---|---|---|---|---|
| Манометр DM 02 | 0/3 | 3/3 | 0 | 4 с |
| Датчик давления ДД-420 | 0/3 | 3/3 | 2 | 17 с |
| Манометр с пропусками | 0/3 | 3/3 | 1 | 18 с |

С первой попытки модель ни разу не выполнила все требования сразу. Замечания к первым попыткам: значения не из входа — 6, описание не того объёма — 6, заголовок длиннее 70 символов — 2. После одного повторного запроса и чистки кодом все 9 карточек уложились в требования.

На предыдущей версии промпта (без запрета писать про монтаж и без правил для блока менеджера) замечаний про значения не из входа было 11 на 9 ответов. Уточнение промпта почти вдвое сократило выдумки, но модель стала чаще не добирать объём. Вывод: один промпт модель не удерживает, устойчивость обеспечивает связка «промпт → проверка → один повтор → чистка кодом».

## Ошибки

- Пустое тело, не-JSON, JSON-массив и `specs` не объектом: HTTP 400 и текст, что именно сломано.
- Все поля пустые: HTTP 400 «Нечего собирать», модель не вызывается.
- Нет ключа или нет сети: 503, карточка не собрана.
- Ключ отклонён: 401.
- Лимит Groq: 429. В сообщении сказано, какой лимит кончился (суточный лимит токенов или частота запросов) и через сколько минут повторить, если Groq это сообщил.
- Таймаут: 504.
- Другой статус или пустой ответ: 502.

Тело ответа с ошибкой: `{"error": "..."}`. Для ошибок разбора JSON есть ещё `line` — номер строки, которую форма подсвечивает.

Сообщения стандартного `json` («Expecting ',' delimiter: line 3 column 3») контент-менеджеру ничего не говорят. Поэтому сервис различает частые случаи и объясняет их словами: текст вместо JSON, JSON обрезан при копировании, пропущена запятая (подсвечивается строка, где её надо поставить, а не следующая), лишняя запятая, незакрытая кавычка. Форма замечает битый JSON ещё до отправки: поле краснеет, а под ним появляется подсказка. Ответы на каждый случай лежат в `examples/invalid_json.md`.

## Тесты

`pytest` не ходит в Groq: вместо модели подставляется заготовленный ответ. 15 тестов покрывают сценарии из пункта 5 задания и ошибки, найденные на живых ответах модели:

- пустые поля и строка из пробелов дают «данных нет»;
- битый JSON даёт 400 с понятной причиной и номером строки; пустая форма — 400 «Нечего собирать»;
- давление 2,5 МПа, которого не было во входе, вырезается, а 0–1,6 МПа остаётся;
- единица, которой нет во входе, не дописывается, и от вырезанного значения не остаётся обрывков;
- заполненный класс точности нельзя назвать «данных нет»; «по назначению данных нет» при заполненном описании вырезается;
- чужая резьба словами и «промышленные условия» уходят в список вырезанного с пояснением;
- фраза с неразрывными пробелами находится и вырезается;
- повторы одного диапазона и одних и тех же пропусков схлопываются;
- список чужих «параметр: данных нет» схлопывается в одну пометку;
- при одном названии на входе запросов всё равно 3–5, а слово «магазин» не путается с «газ»;
- блок для менеджера, повторяющий описание, заменяется на «Подходит для задач… При подборе важны…»;
- сообщение о лимите Groq говорит, какой лимит кончился и когда повторить.

## Ограничения

- Мягкие обобщения без чисел и без слов-маркеров проверка не ловит: «соответствует требованиям к измерительным приборам», «совместим с большинством систем автоматизации», «удобен при ограниченном пространстве». Такие фразы остаются на вычитку контент-менеджеру.
- Проверка бывает и строже, чем нужно: убирает фразы, которые в целом верны, но не подтверждены входом (например, что 4–20 мА — распространённый промышленный сигнал). Поэтому вырезанное не пропадает молча, а показывается с возможностью вернуть.
- Пересказ, который не сводится к числу, единице или слову-маркеру, проверка не поймёт: «резьба на четверть дюйма» вместо «четвертьдюймовая». Строчные «в», «м», «а» после числа не считаются вольтами, метрами и амперами, иначе «2088 в процессах» ломается. Маркеры ищутся только с начала слова: «газ» не находится в «магазине», но и составное слово с маркером в середине пропустит.
- Класс точности сравнивается с числами из характеристик: класс «100» не пройдёт, даже если рядом есть «100 мм».
- Описание на бедном входе получается суховатым: объём добирается фактами и нейтральными фразами, а не живым текстом.
- Задание обещает два товара, но в тексте пришёл только пример манометра. Второй товар, `data/pressure_sensor.json`, составлен мной: условный датчик давления ДД-420 с токовым выходом, питанием, IP и метрической резьбой, чтобы проверить другие единицы и маркировки. Это не паспорт реального изделия. Отдельно `data/manometer_incomplete.json` — тот же манометр без производителя, описания, класса точности и присоединения, чтобы показать «данных нет» и «Что уточнить».

## Что можно улучшить

- Проверка единиц измерения. Сейчас значения переносятся как есть, поэтому «0–1,6» без единицы или «100 км/ч» в диаметре корпуса попадут в карточку без предупреждения. Варианты, от простого к сложному:
  - справочник характеристик: для частых характеристик — допустимые единицы (диаметр — мм, см, дюймы; давление и диапазон измерений манометра — Па, кПа, МПа, бар, кгс/см²; питание — В; выходной сигнал — мА, В; температура — °C). Значение без единицы или с неподходящей единицей попадает в «Что уточнить», а в форме единицу можно выбирать из списка, подходящего к характеристике;
  - характеристики, где число без единицы нормально (класс точности, количество, номер, исполнение), помечаются в справочнике отдельно, чтобы не давать ложных предупреждений;
  - отдельный проверочный запрос к модели: «подходит ли единица к характеристике и типу прибора». Модель только помечает сомнительные пары и не исправляет значение — исправлять по-прежнему должен человек. Такой запрос покрывает характеристики, которых нет в справочнике, но стоит денег и времени, а его ответ тоже нужно сверять, поэтому основой лучше сделать справочник, а модель — запасной проверкой.
- Объём описания добирать вторым запросом к модели с перечнем недостающих фактов, а не нейтральными фразами: текст будет живее.
- Заголовок собирать кодом по шаблону «название, производитель, главная характеристика» вместо того, чтобы просить модель.
- Несколько провайдеров за тем же протоколом `LLMClient`.
- Более точная проверка пересказа, который не сводится к числу, единице или слову-маркеру.
- Пакетная генерация папки с товарами из интерфейса, не только скриптом.
- Учёт токенов и очереди. Для локального прототипа это не нужно.
